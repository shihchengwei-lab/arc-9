## result.任務答案

**目前下載已修正；刪除仍有越權缺口。必要改動應集中在刪除入口。**

下載只接收一個 `file_id`，由服務取得檔案 handle，檢查該 handle 的 read 權限，再以同一個 handle 讀取。在題目保證 handle 不改指的範圍內，獲准的檔案就是實際讀取的檔案。驗證紀錄也支持這個結論，不能將既有版本的下載缺口沿用到目前版本。

刪除仍讓使用者分別指定「拿來檢查權限的檔案」與「實際刪除的檔案」。紀錄已確認，使用者可以用對 A 的 delete 權限刪除沒有權限的 B，因此未滿足任務要求。

必要安排是讓刪除只使用一個權威檔案對象：從 `file_id` 取得服務持有的檔案 handle，通過 `authorize_delete(U, handle)` 後，以同一個 handle 刪除。不要讓請求另外提供可改變刪除對象的 ID。下載仍檢查 read，刪除仍檢查 delete，兩項權限保持獨立。

### 條件結果：已滿足

1. **下載具備實際讀取檔案的 read 權限。**
   - 來源：已確認的承諾與範圍。
   - 依據：目前下載對同一個 handle 先呼叫 `authorize_read`，通過後再讀取。
   - 驗證紀錄：下載 A 取得 A；指定 B 會在讀取前被拒絕；額外 `storage_key` 欄位被拒絕。
   - 適用範圍與成立條件：限題目所述目前下載流程；服務持有映射，handle 在操作期間不改指。

2. **下載不再讓請求獨立選擇授權對象與讀取對象。**
   - 來源：不能用對 A 的權限讀取 B。
   - 依據：入口只接收 `file_id`，實際讀取對象由服務取得的同一 handle 決定。
   - 適用範圍與成立條件：目前下載入口及題目所列限制。舊版可獨立指定 `route_file_id`、`body_storage_key` 的成因已移除。

3. **兩種操作各自使用相應權限。**
   - 來源：read 與 delete 獨立決定。
   - 依據：下載檢查 read；刪除入口檢查 delete。材料沒有將兩者合併為同一規則。
   - 適用範圍與成立條件：此項只表示權限種類分別使用；刪除檢查的檔案對象仍有下述缺口。

### 條件結果：未滿足

1. **實際被刪除的檔案必須具有 delete 授權。**
   - 來源：刪除須具備實際檔案的 delete 權限；不能用對 A 的權限刪除 B。
   - 依據：刪除入口仍先以 `route_file_id` 對應的 A 檢查 delete，再刪除 `body_delete_file_id` 對應的檔案；兩個值由使用者獨立指定。
   - 已觀察反例：U 對 A 有 delete、對 B 沒有；route 指 A、body 指 B，仍能刪除 B。
   - 影響：使用者能使刪除越出其獲准的檔案範圍。
   - 成因：入口允許建立「授權 A、操作 B」的組合，執行刪除的位置沒有受到同一授權對象約束。

   **補足條件的候選安排：**
   - 建議安排：刪除入口只接受一個 `file_id`；服務取得 handle，檢查該 handle 的 delete 權限，並刪除同一 handle 所指的檔案。
   - 責任位置：入口移除第二個可獨立指定的刪除對象；執行流程讓授權與刪除共用服務取得的同一對象。
   - 前提：沿用題目已保證的穩定映射與 handle。若底層刪除只能接受 ID，該 ID 應直接取自已授權的同一檔案物件。
   - 效果：使用者不能再建立「通過 A 的檢查，卻刪除 B」的操作。

   **替代安排：**
   - 若另有保留雙欄位介面的需求，可在任何刪除前拒絕兩個欄位指向不同檔案的請求，後續仍只使用同一個已授權的服務端檔案對象。
   - 這是保留既有介面時的替代方案，與移除第二個欄位不必同時採用。題目沒有提出必須保留雙欄位的需求；單一對象安排直接消除了需要持續檢查的非法組合。

### 必要安排與驗證

必要安排僅對應尚未滿足的刪除條件：

3. 修正後核對：獲准刪除 A 時操作 A；直接指定無 delete 權限的 B 時，在刪除前拒絕；原本「route A、body B」的請求不能刪除 B。

### 可選改善

- 若採單一 `file_id` 介面，可明確拒絕舊的 `body_delete_file_id` 欄位，避免呼叫端誤認該欄位仍有效。達成授權安全的核心是該欄位不能改變實際刪除對象；拒絕欄位則讓介面行為更清楚。
- 可增加「只有 read」與「只有 delete」的權限組合驗證，防止日後誤把兩項規則合併。這是保護既定權限獨立性的補充驗證，並非本題已發現另一項實作缺口。
