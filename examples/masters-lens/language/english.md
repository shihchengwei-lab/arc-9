- **Do not implement this proposal as written.** Its retry behavior conflicts with the requirement that corrected customer data survive older work. For example, job A writes some rows and stops; corrected job B finishes; A is redelivered and overwrites B’s names and phone numbers. A `job_id` identifies the job but does not establish which customer values may replace others. Separately committed rows and completion status also allow customer changes to exist while the job remains incomplete.

- **Put the guarantees at the database write boundary.** Define “newer” explicitly; accepted upload order is one candidate. Give each accepted import a durable sequence and each customer a last-applied import sequence, then permit updates only from a newer import. For this bounded workload, consider committing customer changes and the job’s completed status in one transaction. Retrying a completed `job_id` should return its stored result without applying the file again; a failed transaction should leave a retryable job with no committed customer changes. This arrangement requires an explicit policy for overlapping uploads and any customer edits outside imports.

- **Reduce the initial design to the existing backend, CSV handling, and database operations.** No scheduled format requirement supports a strategy factory yet. The supplied volume does not establish a need for a queue or worker. Measure a representative 500-row import against the request timeout before choosing background execution; retain the same ordering, atomicity, and retry guarantees if background processing proves necessary.
