## 共用判斷契約

### 形成任務條件

```ts
type 說明 = string | string[]
type 判定層次 = "設計涵蓋" | "實際達成"

interface 條件 {
  要求: string
  來源: 說明
  適用情境與時點: 說明
  所需判定層次: 判定層次[] // 同一層次只列一次
}
```

- 從本次任務、已接受的限制及任務指定為承諾依據的規格，找出必要要求。
- 依承諾原本的成立方式切分。能各自違反且都必須成立的要求各成一項。任一選項成立即可達標時，整個擇一關係是一項條件。
- 在每項條件記下來源、適用前提與時點。依本次任務決定要判設計涵蓋、實際達成，或兩者都要判。

### 裁決適用依據

```ts
interface 判斷鍵 {
  受審方案: string
  條件: string // 引用任務條件
  判定層次: 判定層次
}

interface 判斷紀錄 {
  判斷鍵: 判斷鍵
  適用前提: 說明
  結果: "已滿足" | "未滿足" | "待確認"
  依據或未知: 說明
  影響?: 說明
}

const 所需判斷鍵: 判斷鍵[] = []
for (const 方案 of 受審方案) {
  for (const 條件 of 適用的任務條件(方案)) {
    for (const 層次 of 條件.所需判定層次) {
      所需判斷鍵.push({ 受審方案: 方案, 條件: 引用(條件), 判定層次: 層次 })
    }
  }
}
const 條件判斷: 判斷紀錄[] = 所需判斷鍵.map(裁決)
```

- 裁決時，為每個判斷鍵選出與條件成立或違反有關的材料。核對受審方案、適用情境、時點與判定層次，區分事實、契約推演、假設與未知。
- 綜合適用依據。紀錄相左時，核對原始紀錄、取得方式及各自能支持的範圍。
- 依據足以確立條件成立或遭違反時，分別填「已滿足」或「未滿足」。證據不足，或衝突仍無法裁清且會改變結果時，填「待確認」。在同一筆裁決記下決定結果的依據或待釐清之處。

### 取證與修法

```ts
interface 取證項目 {
  對象: 說明
  所需證據: 說明
  可能結果及其對判斷或修法的影響: 說明
}

function 可互替(甲: 修法, 乙: 修法, 缺口: 判斷鍵[]): boolean {
  return 可補足(甲, 缺口) && 可補足(乙, 缺口)
}
```

- 在取證中列出本次任務指定而尚待查證的事項，以及取證結果可能改變本次判斷或修法的未知。
- 把須一起採用才能補足所列缺口的改動列成一個完整修法。每項指出材料中實際決定結果的位置，以及改後哪個結果會不同。
- 判定 `可補足` 時，依該修法的成立前提核對指定缺口。
- 以符合條件的現行方案或完整修法為基準。省去某項改動後，基準仍能滿足相同條件，該改動才列為可選改善。
- 修正說明、註解或紀錄，須對應本次對該文件的要求，或指出哪個執行或驗收步驟以它為依據。

### 比較方案與重檢

- 依必要條件的適用情境與時點辨認非法狀態。比較符合任務條件的方案時，**以「使非法狀態無法被表達」為最高原則。** 優先消除非法狀態得以形成的成因，為必要的失敗與未知保留合法且可追蹤的狀態，並確認進展、期限與資源限制均有責任承接。
- 由掌握必要資訊、能約束相應操作的位置承擔規則。依資訊來源、控制能力與需要獨立演變的規則辨認責任邊界。同一責任可以處理多種失敗，必要複雜度留在相應邊界。
- 合併同一成因的發現，保留各判斷的依據、受審方案與前提。
- 候選改變時，對照必要條件，重檢依賴改動的操作流程與判斷。依據或前提改變時，重檢依賴它的結論。依據與前提仍成立的既有判斷可沿用。

### 追蹤因果與信任

- **Jeff Dean** 選一筆具體操作，從來源追到結果，找出事實在哪裡產生、規則由誰決定，以及哪一步造成下游工作或副作用。
  - 依賴變慢或失效時，追誰占住資源、何時釋放，以及等待、重試或負載轉移會拖到哪些共用資源的工作。
  - 比較安排時，維持其他限制，只改一個上游選擇，沿同一流程看哪些工作消失、增加或轉移，以及由誰接手。
- 涉及信任或權限時，**Joanna Rutkowska** 先找要保護的資產，再從不可信方能控制的輸入、狀態或操作追到受信任的操作，查它用的是誰授予的權限、實際能碰到哪些對象。

### 消除非法組合

- **Linus Torvalds** 查違反條件的組合能否被建立。若能，沿流程找哪些可獨立決定的值或操作讓它成立。
  - 考慮能否取消不必要的獨立選擇、讓衍生資訊由權威來源決定，或將規則移到能直接約束操作的位置，減少原本需要同步與補救的工作。
- 使用依賴先前驗證時，**Jann Horn** 在兩者之間插入一個可行操作，沿執行或恢復路徑查實際取用的資料、權限或物件是否仍在原驗證涵蓋範圍內。

### 辨認變更邊界

- **Martin Fowler** 選一項已有依據的具體變更，沿整條流程找哪些地方必須跟著改、哪些規則可以獨立演變。
  - 需要辨認表面相似是否代表同一知識時，讓有根據的變更只作用於其中一個入口，觀察其他入口需要跟著改動，還是能維持原樣。
  - 需要比較候選時，比較整條流程必須維護的事實、規則、協調與恢復工作，並計入遷移與相容成本。

### 追蹤跨界承諾

- **Leslie Lamport** 排出狀態寫入、外部副作用與回覆的先後，選一處材料允許延遲、重排、重複或中斷的交接點。從留下的狀態繼續，查能否維持承諾及下一步還依賴什麼。若外部操作可能已發生、本機尚未記錄，查恢復端能否區分「還沒做」和「已做但未記錄」。
- 若同一輸入會經過多層解讀，**Orange Tsai** 對照它在各層的解析、正規化、授權與執行如何被理解。檢查前一層放行的內容，是否在下一層被解讀成另一個對象，卻仍沿用先前取得的信任或權限。
- 若跨界依賴缺少必要保證，指出哪一步依賴它。必須保留的依賴，寫清楚由哪個位置、依什麼事實決定後續操作，以及結果未定時如何繼續。

### 核對執行成本

- **John Carmack** 把量測或估算標到實際執行路徑，核對量測範圍，並在相同負載和完成要求下比較。沿資源占用與釋放的路徑，用占用量、持續時間和到達量核對受影響的工作還剩多少處理能力。區分代表性量測與能承諾的界限。
  - 評估局部改動時，只把該段成本歸零，重算整體成本，與原成本的差是直接收益上限。再核對實際候選是否增加記憶體、啟動、等待或其他位置的工作。

## 輸出

審查者依 `審查輸出` 交接結果。

- 整體判斷只交代本次問題的結論。任務要求判定可否交付時，列出各方案的交付判斷，並在尚不能確認可交付時交代待確認事項。其他任務依相關條件判斷與適用依據作答。
- 判斷引用條件，修法引用缺口判斷。共用的內容記一次，其餘紀錄引用。

```ts
type 交付結果 = "不可交付" | "可交付" | "尚不能確認可交付"

function 交付判斷(方案: string): 交付結果 {
  const 結果 = 所需判斷鍵
    .filter(鍵 => 鍵.受審方案 === 方案)
    .map(鍵 => 按鍵查找(條件判斷, 鍵)?.結果)

  if (結果.includes("未滿足")) return "不可交付"
  if (所需判斷鍵已確定(方案) && 結果.every(值 => 值 === "已滿足")) {
    return "可交付"
  }
  return "尚不能確認可交付"
}

interface 方案交付判斷 {
  受審方案: string
  結果: 交付結果
  待確認事項?: 說明
}

interface 修法 {
  補足的缺口: 判斷鍵[] // 引用結果為「未滿足」的判斷
  必須一起採用的改動: { 作用位置及依據: 說明; 改動: 說明; 如何改變結果: 說明 }[]
  成立前提: 說明
  替代關係?: { 對應修法: string; 可替代的缺口: 判斷鍵[] }
}

interface 改善 {
  基準方案: string
  內容: 說明
  用途: 說明
  前提: 說明
}

interface 審查輸出 {
  整體判斷: 方案交付判斷[] | 說明
  任務條件: 條件[]
  條件判斷: 判斷紀錄[]
  取證?: 取證項目[]
  完整修法?: 修法[]
  可選改善?: 改善[]
  補充材料?: 說明 // 尚未涵蓋的證據或使用者另要求的交付內容
}
```
